Why the list was wrong

This matters more than the list itself, because the same mistake will happen again on the next audit unless the cause is understood.

  • Postgres keeps two different row counts. One is the truth (count(*), which walks the table). The other is a fast running estimate (n_live_tup) that the database updates as a side effect of its housekeeping.
  • The estimate on this database is currently meaningless. Every one of the 26 tables reports n_tup_ins = 0 — zero rows ever inserted — which is impossible for a table holding 1.6 million rows. Every table also reports last_analyze, last_autoanalyze, last_vacuum and last_autovacuum as empty. That combination means the statistics were wiped and have not been rebuilt.
  • The read counters survived, and they tell the real story. The same statistics view still shows idx_scan and seq_scan — how many times each table was actually read. Those numbers are large and recent for the tables that matter, which is the strongest single piece of evidence that these tables are in live use.
  • The large sizes were read backwards. A 286 MB table reported as empty looks like abandoned bloat. It was simply a 286 MB table with 1.6 million rows in it.

The DROP list

This is the section you were meant to hand to the orchestrator to execute.

There are no DROP TABLE statements, because nothing qualified.
Zero of the 26 candidates met the test for dead. Every one holds real rows, and most are read by a live view, a database function, or code in the Station repository. Running the purge as specified would have destroyed 4,313,020 rows, including the entire adjusted daily price history.

The five that still need a decision

These are not dead, but they are not obviously healthy either. None should be dropped on this evidence; each needs one specific thing checked first.

plant_master_backup_predupe — 212 records that exist nowhere else

The closest thing on the list to genuine garbage, and it still is not. Its name says it is a throwaway backup, but its 666 keys are all distinct and 212 of them are absent from the live plant library, while the live library contains nothing that is not also in the backup. So the de-duplication pass removed 212 plant records, and this table is the only remaining copy of them. Decide whether those 212 were junk before it goes.

insider_trades and sector_performance — feeds that stopped

Both hold thousands of real rows and both stop dead on 9 June 2026. That is a broken feed, not a dead table: whatever was loading them stopped three months ago. The fix is to find out why the loader stopped, not to delete the history it already collected.

urth_cache and site_marks — Urth data, judged from the wrong repository

These belong to Urth Landscaping, not Scintilla. I grepped the Scintilla Station repository for them and found nothing, which proves only that Scintilla does not use them. A separate Supabase project named urth-live was created on 18 August 2026 — the same day urth_cache was last written — which suggests Urth moved to its own database and these may be the leftovers. That has to be confirmed against the Urth codebase before anyone drops them. Both also carry row-level security policies, meaning an application was designed to read them as a specific signed-in user.

What I could not rule out

  • Reads from outside the database. A view or function that mentions a table proves a dependency. The absence of one does not prove nothing reads it — an application can query a table directly. That is why the read counters matter, and why every table here shows reads above zero.
  • Code outside the Station repository. The grep covered the Station working tree only. The Hub clone, the chart API service on Fly.io, and the Urth codebase were not searched, so a zero in the code-refs column is not proof of disuse.
  • When the statistics were reset, and by what. Something wiped this database's table statistics and nothing has rebuilt them. Until that is fixed, any future audit that trusts n_live_tup will produce this same wrong list.

-- Result: n_live_tup = 0 for 25 of 26. n_tup_ins = 0 for all 26 --

-- 3. What depends on each table: views, matviews, functions, foreign keys,
--    triggers and row-level-security policies.
select c.t,
  (select string_agg(distinct v.viewname,', ') from pg_views v
     where v.schemaname not in ('pg_catalog','information_schema')
       and v.definition ~ ('\y'||c.t||'\y')) as views,
  (select string_agg(distinct m.matviewname,', ') from pg_matviews m
     where m.definition ~ ('\y'||c.t||'\y')) as matviews,
  (select string_agg(distinct p.proname,', ') from pg_proc p
     join pg_namespace n on n.oid = p.pronamespace
     where n.nspname not in ('pg_catalog','information_schema')
       and p.prosrc ~ ('\y'||c.t||'\y')) as functions,
  (select string_agg(distinct conrelid::regclass::text,', ') from pg_constraint
     where contype = 'f' and confrelid = ('public.'||c.t)::regclass) as fks,
  (select count(*) from pg_trigger tg
     where tg.tgrelid = ('public.'||c.t)::regclass
       and not tg.tgisinternal) as user_triggers,
  (select count(*) from pg_policies pol
     where pol.schemaname = 'public' and pol.tablename = c.t) as rls_policies
from cands c order by c.t;

-- Result: 8 tables feed a view or materialised view, 11 are named inside
-- database function bodies, 20 carry RLS policies. No foreign keys point
-- at any of them and none carry user triggers.
-- 4. Newest data in each table that has a date or timestamp column.

What I recommend instead of the purge

  • Cancel this purge outright. The candidate list is invalid at its root, not merely too long. There is no smaller safe subset of it.
  • Rebuild the statistics first. Run ANALYZE across the database. Until that happens every row-count estimate on this project is fiction, and the next audit will generate the same list again.
  • Re-run the audit afterwards. With honest statistics, a real dead-table list may well exist — but it will be a different list, built from different tables than these.
  • Treat the stalled feeds as the actual finding. Three feeds you care about have stopped: insider trades and sector performance in June, the put/call ratio back in 2019. That is the genuine problem this audit surfaced.
