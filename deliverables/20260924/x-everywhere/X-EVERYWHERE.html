X everywhere — the crop, and one bridge in four browsers

The X pane was cropping the wrong part of the captured picture whenever the X window was not the same shape as the capture — which is exactly what happens on the iMac when you resize that window. That is fixed at the root. The bridge also becomes one folder that Chrome and Brave read on both Macs, and it updates itself from that folder without you visiting four browsers. Nothing is deployed and nothing has been copied into the folders your browsers load: this sits on branch station/x-everywhere-20260924, built from 81e2ab7.

1 · What was actually wrong

When Chrome or Brave captures a tab, it does not hand back a picture shaped like your X window. It shrinks the window to fit inside a ceiling — 16:9 — keeps the proportions, and centres the result. So whenever your X window is not 16:9, the captured frame contains your window in the middle with black bars down the sides.

Both viewers then worked out where the timeline column sat by dividing each direction on its own: frame width ÷ window width for across, frame height ÷ window height for down. Those two numbers are only the same when the window and the frame are already the same shape. With bars present they are not, and the bar width was never subtracted at all. The crop therefore started to the left of the column and ran far too wide.

Two things made this invisible until now. On a 1× screen the frame is small enough to escape the ceiling entirely, so there are no bars and the old sum is right. And the shape M29 was soaked on — this MacBook, one window family — is within a whisker of 16:9, so the error was about 2 pixels. On the iMac, a 2× screen, the window is always scaled down to the ceiling, so the ceiling's shape decides everything.

Which of the suspects it was

  • Letterboxing — yes, this is the fault. The bars are 615 px wide each side in the tall-window case, and the old sum had no term for them.
  • 2× screen — the precondition. It is what pushes the frame over the ceiling so the ceiling's shape governs. On a 1× screen the same window was always correct.
  • Browser zoom — not a factor. Zoom changes the window's and the column's measurements together, so the crop lands on the same fraction of the picture. There is a test for exactly that.
  • Also found, and also fixed: the two capture paths asked for different ceilings — 1920×1080 for the relay, 2560×1440 in the tab — so the same window arrived at two different sizes depending on which path fed the pane. That is your “some mismatch”. Both now ask for the same thing.

2 · The fix

  • One scale for both directions, plus the bar offsets. A single helper works out how the window sits inside the frame, and the crop is measured from the edge of the picture rather than the edge of the frame. Where the old sum was right, the new one returns the identical numbers — when the shapes match, the offsets are zero — so nothing that works today can change.
  • The crop is clamped inside the picture. It can never read a black bar, at any window size.
  • Both viewers carry the same helper. A test compares them, so the pane and the shell cannot drift apart again.
  • The last-resort whole-window draw now says so. It writes whole X window · crop missed the picture in the pane's status line and clears it the moment the crop lands. That is the state you saw and read as the product; it can no longer sit there silently.

It is not switched on for the Station pane in this change, and here is the real reason. The Station pane's video is captured by the extension's hidden background page, not by the X tab. The browser will only accept a crop target that was minted inside the captured tab, and an extension can only pass plain text between those two places, not a crop target. So switching it on means moving the capture into the X tab itself — which changes the live link that feeds your pane, and the only way to prove a change to that link is to watch a real session on your screen. I have built everything up to that line: the pane already honours a track that arrives cropped (sourceCropped, drawn whole, with no mapping at all), and the bridge reports what each browser can do. The remaining step is a supervised session with the coordinator, not a guess. Until then the corrected mapping is what runs, and it is correct at every shape in the table above.

3 · One folder, four browsers, and a bridge that updates itself

The bridge now reads its own folder's version number once a minute. When the folder holds a newer version than the copy a browser is running, that browser reloads the extension by itself. Publishing an update becomes a file change, not a trip to four browsers.

  • It waits for an idle pane. A reload drops a live capture, so if the pane is being fed the update waits until it is not. You will never watch the pane die because a file changed.
  • It cannot go backwards. Only a strictly newer version triggers a reload; an equal or older folder is ignored, as is a folder it cannot read.
  • This needs one new permission, alarms, and nothing else. Version is now 0.7.19.

Where the shared folder should live — a proposal, nothing moved

I checked how today's folder reaches the iMac: it does not. /Users/alanharvey/Scintilla/SCINTILLA X Bridge is a plain local folder, in nothing that syncs. On this Mac, iCloud Drive is signed in, and Google Drive is signed in for three accounts.

My recommendation is iCloud Drive, at ~/Library/Mobile Documents/com~apple~CloudDocs/SCINTILLA/X Bridge, with the folder set to Keep Downloaded on both Macs — an unpacked extension has to be real files on disk, and iCloud will otherwise evict them to the cloud and the extension will fail to load. Google Drive would work too, but its files live behind a sync layer that can stall, and a stalled read of manifest.json is a bridge that will not start. I have not created, moved or copied anything. Say the word and the coordinator sets it up; the clicks below assume the shared folder exists and refer to it as THE SHARED FOLDER.

4 · Your one-time setup — exact clicks

Do these once. After that, updates arrive on their own.

A · Chrome on the iMac (it has never been set up)

  1. Open Chrome on the iMac.
  2. Click the address bar, type chrome://extensions and press Return.
  3. Top right of that page there is a switch labelled Developer mode. Click it so it turns blue. Three buttons appear at the top left: Load unpacked, Pack extension, Update.
  4. Click Load unpacked. A Finder window opens.
  5. Press ⌘⇧G, paste the path of THE SHARED FOLDER, press Return.
  6. Click the folder once so its name is highlighted — do not open it and do not pick a file inside it — then click Select.
  7. Success looks like: a card appears titled SCINTILLA Station X Bridge, version 0.7.19, with an ID: line and its own toggle switched on. If a red Errors button appears, stop and send me the text — the folder is wrong or incomplete.
  8. Click the puzzle-piece icon to the right of the address bar, find SCINTILLA Station X Bridge in the list, and click the pin outline beside it so it turns solid. Its small icon now sits next to the address bar.
  9. Open a tab on x.com and let the timeline load.
  10. Click that pinned icon once (or press ⌥⇧S).
  11. Success looks like: within a few seconds the Station X pane shows the timeline, the pane's status line reads live, and a small grey badge next to it reads Chrome · iMac 5K.

B · Chrome on this MacBook (move it off the old folder)

Why this matters: if both the old folder and the shared folder stay loaded, two bridges fight over the same X tab and the pane will flicker between them. Remove the old one first.
  1. Open Chrome, go to chrome://extensions.
  2. Find the card SCINTILLA Station X Bridge showing version 0.7.16. Click Details and check the Loaded from path ends in station-x-bridge-c71. That is the one to remove.
  3. Go back, click Remove on that card, then Remove again in the small confirmation box.
  4. Turn on Developer mode if it is not already on, click Load unpacked, and pick THE SHARED FOLDER exactly as in steps 5–6 above.
  5. Success looks like: exactly one SCINTILLA Station X Bridge card, version 0.7.19, loaded from the shared folder. Pin it, then link an x.com tab as in steps 8–11 above; the badge should read Chrome · MacBook Pro.

C · Brave, on both Macs (confirm the folder)

  1. Open Brave, click the address bar, type brave://extensions and press Return.
  2. Turn on Developer mode (switch, top right).
  3. Find SCINTILLA Station X Bridge and click Details. Read Loaded from.
  4. If it already reads THE SHARED FOLDER: you are done here — just check the version says 0.7.19 after the coordinator publishes it, or click Update once to hurry it along.
  5. If it reads /Users/alanharvey/Scintilla/SCINTILLA X Bridge or anything else: click Remove, confirm, then Load unpacked and pick THE SHARED FOLDER.
  6. Success looks like: one card, version 0.7.19, loaded from the shared folder, and the pane badge reading Brave · iMac 5K or Brave · MacBook Pro depending on the Mac.
After all four: nothing to click ever again for an update. Each browser checks the folder every minute and reloads itself when it is newer — and only while nothing is being fed to a pane.

5 · The source badge

The pane now prints, in small grey letters beside its status line, which browser and which Mac is feeding it — Brave · iMac 5K, Chrome · MacBook Pro, and so on. When one browser works and another does not, that sentence stops being a guess.

  • Brave is detected properly rather than being mistaken for Chrome (Brave deliberately reports itself as Chrome in the usual place).
  • The Mac is named from the screen it is running on. If you want an exact name instead — “iMac (desk)” — it can be set per machine and it wins over the guess.
  • The badge only ever prints what the bridge measured. It is not saved anywhere and changes no setting.

6 · What could still fail

  • iCloud evicting the folder. An unpacked extension must be real files. If macOS moves them to the cloud, the browser cannot load the bridge. Keep Downloaded on both Macs is the guard; if the shared folder ends up on Google Drive instead, a sync stall has the same effect.
  • The Station relay is still not cropped at the source. The mapping is correct now, but it depends on the X tab reporting where its column is. If X changes its page structure, that measurement can go wrong in a different way — and that is source-side geometry, untouched by this change.
  • Nothing here was proven against a live capture. The arithmetic, the fallback wording, the self-reload and the badge are proven offline; a real tab capture needs a visible window on your screen, which is not allowed in this unit.
  • An update waits for an idle pane. If a pane feeds continuously, the reload waits — it will land the next time the pane is idle or the browser restarts.
  • Two browsers on one Mac can both link the same X tab. Whichever links last wins. The badge now tells you which one it is.
  • Text sharpness is capped. Both paths now ask for at most 2560×1440, so on the 5K screen the pane is drawing from a scaled-down picture. Raising it costs CPU; I did not change the ceiling upward on my own.
  • One pre-existing test failure, not mine. A pane-x test about crop heartbeats marking a dead receiver as live already failed at 81e2ab7 and still does. It concerns the older pane, not the shell the deck mounts. Left alone deliberately, reported rather than quietly patched.
